- **2026-09-29** — `band_members_insert` RLS policy (in `supabase/migrations/0002_rls.sql`) only checks `user_id = auth.uid()`, with no DB-level check that the joining user actually knows the band's `invite_code`. Any authenticated user can currently self-join any band by guessing/enumerating its UUID — invite-code validation exists only in the app layer's join flow, not enforced at the database boundary. Accepted as-is for Phase 1 (schema/RLS review, not app code) since the MVP's client never exposes a raw insert path. **Must fix before Phase 5** (band collaboration ships): convert the join flow to a `SECURITY DEFINER` RPC (e.g. `join_band(p_invite_code text, p_display_name text)`) that validates the invite code server-side before inserting, so the raw `band_members` insert is never independently reachable.

- **2026-10-08** — `apps/mobile/app/band-setup.tsx`'s "create band" flow does two sequential inserts (`bands` then `band_members`) with no transaction. If the first succeeds and the second fails (network blip), the user sees a clear error and isn't stuck (redirected back to band-setup by `app/index.tsx`'s gating), but the orphan `bands` row persists with no members and no UI path to reclaim it — retrying just creates another orphan. Accepted for MVP: this needs a flaky-network window to trigger, and the fix (either a `SECURITY DEFINER` RPC doing both inserts atomically, or client-side detection/reuse of the orphaned band) is real scope beyond this phase. Revisit alongside the `join_band` RPC already planned for Phase 5 (see the 2026-09-29 band_members_insert entry above) — both are "band creation/join should be one atomic server-side operation, not raw client inserts."
- **2026-10-08** — Phase 3a (mobile auth + band setup) end-to-end manual verification against the local Supabase stack, via `npx expo start --web` and real magic-link emails read from Mailpit (not mocked). Found and fixed two real RLS bugs that Phase 1's pgTAP suite never caught, because pgTAP exercised `is_band_member()`-gated reads and `service_role` (which bypasses RLS) — this was the first time any `authenticated`-role client request hit these specific policies for real:
  1. **Band creation was completely broken.** `bands_select` only allowed `is_band_member(id)`. Creating a band inserts the `bands` row, then `band_members` — but `supabase-js`'s `.insert().select()` does `INSERT...RETURNING`, and Postgres re-checks the SELECT policy on the new row before returning it. At that instant the creator isn't a `band_members` row yet, so every band creation failed with "new row violates row-level security policy for table bands", 100% of the time, regardless of app code correctness. Fixed in `supabase/migrations/0004_bands_select_own_created.sql`: `bands_select` now also allows `created_by = auth.uid()`.
  2. **Joining a band via invite code was impossible.** Same root cause, different table: a non-member can't `SELECT` a band by `invite_code` to find its id, because `bands_select` (even after fix #1) still only grants access to members or creators — not "anyone who knows the invite code." Fixed in `supabase/migrations/0005_join_band_rpc.sql`: added a `SECURITY DEFINER` `join_band(p_invite_code, p_display_name)` RPC that looks up the band bypassing RLS, then inserts membership. `apps/mobile/app/band-setup.tsx`'s join flow now calls this RPC instead of raw table queries. This also closes most of the gap logged 2026-09-29 (`band_members_insert` had no DB-level invite-code check) — the client no longer has any reason to call the raw insert for joining, though that raw insert path itself is still technically reachable and not yet locked down; full closure of that gap (restricting `band_members_insert` so only `join_band`/band-creation can populate it) is still deferred to Phase 5 as originally planned.
  Both fixes verified live: created a band as one user, joined it as a second user via its real invite code, both landed on the gated home screen with the same `band_id`. Sign-in verified with real Mailpit emails for three different addresses. `emailRedirectTo` added to `signInWithOtp` (using `window.location.origin`) since the default `redirect_to` from local Supabase config pointed at an unreachable port — without it, the session token was never readable by the app (this would have blocked literally every web/native magic-link sign-in, not just testing). Native (iOS/Android) deep-link handling was NOT tested — `detectSessionInUrl: true` only covers the web flow tested here.
- **2026-10-09** — Phase 3b (rehearsals list, upload, playback) end-to-end verification against the local Supabase stack and the Phase 2 worker running locally. Found and fixed one real infra bug, confirmed two real gaps (not fixed, logged), and proved the full pipeline works:
  1. **Worker had no CORS headers.** Every browser-originated fetch to `http://127.0.0.1:8000/process` (and `/health`) failed with a CORS error, completely silently from the UI's perspective (the `upload.tsx` error state would just say "Failed to fetch"). Native apps aren't subject to CORS so this never surfaces on-device, but it would have totally broken the web client path this phase's own testing (and any future web admin/dev tooling) relies on. Fixed in `services/worker/app/main.py` with `CORSMiddleware` (`allow_origins=["*"]` — the real auth boundary is the `X-Worker-Key` header, not request origin).
  2. **File picker automation limitation.** `expo-document-picker`'s web implementation triggers either a native OS file dialog or the File System Access API, neither of which is reachable from DOM-level browser automation (same category as any OS-native dialog). Worked around by replicating `upload.tsx`'s exact sequence (storage upload → `rehearsals` insert → `/process` trigger) via direct `fetch` calls with a synthetic in-memory WAV file, using the same signed session token the real UI would use. This proves the backend integration end-to-end; the picker button itself is Expo's own official, separately-maintained library, not code this project wrote — native device testing (where the real OS dialog works normally) is the actual proof for that one interaction, deferred to Victor per every previous phase's device-testing pattern.
  3. **Confirmed working, live:** uploaded a real WAV, rehearsal appeared in the list instantly at `status=uploaded`; triggered `/process`; **list status flipped to `ready` with no page reload** — Realtime subscription confirmed working end-to-end; opened the rehearsal, clip appeared with the correct `kind` classification (`talk`, since the 0.5s test tone is well under `min_take_sec`); tapped Play — confirmed via network inspection that the signed URL was fetched with a real `206 Partial Content` range request (the browser audio engine actually loading real audio data, not a no-op).
  4. **Not fixed, logged for later:** `upload.tsx`'s storage-upload-then-DB-insert is two sequential calls with no transaction — same class of gap as Phase 3a's band-creation orphan-row risk (2026-10-08 entry above). If the insert fails after a successful upload, the storage object is orphaned with nothing pointing at it. Accepted for MVP, same reasoning as the earlier entry.

- **2026-10-13** — Phase 4b (waveform editing) end-to-end verification against the local Supabase stack. Found and fixed two real bugs:
  1. **Clip selection was completely broken on web.** The clip overlay used `View`'s `onTouchEnd` to detect a tap-to-select. `onTouchEnd` only fires for real touchscreen touch events — a normal mouse click in any desktop or web browser never triggers it at all. Every tap silently did nothing; the drag handles and Split/Merge/Delete buttons (which only render when a clip is selected) were unreachable for any web/desktop user. Fixed by switching to `Pressable`/`onPress`, the same pattern already used for every other tappable element in the app.
  2. **Stale closure in the drag handles** (caught during code review, before manual testing): the `PanResponder` for each handle was created once via `useRef` and closed over `draftStart`/`draftEnd`/`clip` from whichever render first created it. After the first bounds commit, later drags on the same clip would compute deltas from stale base positions. Fixed by reading current values through a ref kept up to date every render, with each drag's base position captured fresh at gesture-grant time.
  3. **Confirmed correct, live, with precise verification (not just visual screenshots):** waveform overlay position/width matched exact pixel math against `start_sec`/`end_sec`/`duration_sec` (checked via computed DOM styles: `left = 47.84px` for `(0.4/5.0)*598`, exact). Split at playhead produced two clips meeting exactly at the playhead time, both `auto_detected=false`. Merge recombined them back into one clip spanning the original range, `auto_detected=false`. Delete removed the row. Drag-to-resize (simulated via real `mousedown`/`mousemove`/`mouseup` events with `buttons:1` set — RN Web's responder system requires that flag to recognize an active drag, not just an app bug) moved `start_sec` by exactly the expected amount for a 20px drag (`0.4 + 20*(5.0/800) = 0.525`, exact match). Real touch-drag on a physical device remains untested, consistent with every previous phase's device-testing deferral.
