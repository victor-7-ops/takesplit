- **2026-09-16** — Adopted the clip confidence score feature (see `docs/superpowers/specs/2026-09-16-clip-confidence-score-design.md`) into Phase 0/4 of the base plan, rather than treating it as a later add-on. Reason: it's cheap to add while writing `detect.py` for the first time, expensive to retrofit once clip schema and UI are built around a binary auto_detected flag.
- **2026-09-16** — Confidence data stored in `rehearsals.detection_params` jsonb rather than a new `clips.confidence` column. Reason: avoids a schema migration for a display-only, non-authoritative value; accepted tradeoff is no SQL-level filtering across clips by confidence tier at MVP scale.
- **2026-09-16** — Skipped the Phase 0 acceptance gate (real-recording accuracy run against HANDOFF.md §3 target) and started Phase 1 immediately, at Victor's explicit request, overriding the "don't start a phase until the previous phase's acceptance passes" rule in CLAUDE.md. Risk accepted: `detect.py`'s default params (`threshold_ratio`, `min_gap_sec`, `min_take_sec`, `pad_sec`, confidence weights) are untested against real rehearsal audio and may need retuning once real recordings are run — that retuning is isolated to `DEFAULT_PARAMS` in `detect.py` and doesn't affect Phase 1's schema/RLS work.
- **2026-09-29** — `band_members_insert` RLS policy (in `supabase/migrations/0002_rls.sql`) only checks `user_id = auth.uid()`, with no DB-level check that the joining user actually knows the band's `invite_code`. Any authenticated user can currently self-join any band by guessing/enumerating its UUID — invite-code validation exists only in the app layer's join flow, not enforced at the database boundary. Accepted as-is for Phase 1 (schema/RLS review, not app code) since the MVP's client never exposes a raw insert path. **Must fix before Phase 5** (band collaboration ships): convert the join flow to a `SECURITY DEFINER` RPC (e.g. `join_band(p_invite_code text, p_display_name text)`) that validates the invite code server-side before inserting, so the raw `band_members` insert is never independently reachable.

- **2026-10-08** — `jobs.run_process` (Phase 2 worker) has a brief partial-read window during idempotent reprocessing: it deletes old `auto_detected=true` clips, then re-inserts new ones one at a time, before finally setting `status='ready'`. A client reading the `clips` table directly during this window (ignoring `rehearsals.status`) could see a partial list. Accepted for MVP since the app should always gate clip-list reads on `status != 'processing'` — not fixed now, revisit if a batched upsert becomes worth the complexity.

- **2026-10-08** — `apps/mobile/app/band-setup.tsx`'s "create band" flow does two sequential inserts (`bands` then `band_members`) with no transaction. If the first succeeds and the second fails (network blip), the user sees a clear error and isn't stuck (redirected back to band-setup by `app/index.tsx`'s gating), but the orphan `bands` row persists with no members and no UI path to reclaim it — retrying just creates another orphan. Accepted for MVP: this needs a flaky-network window to trigger, and the fix (either a `SECURITY DEFINER` RPC doing both inserts atomically, or client-side detection/reuse of the orphaned band) is real scope beyond this phase. Revisit alongside the `join_band` RPC already planned for Phase 5 (see the 2026-09-29 band_members_insert entry above) — both are "band creation/join should be one atomic server-side operation, not raw client inserts."
- **2026-10-08** — Phase 3a (mobile auth + band setup) end-to-end manual verification against the local Supabase stack, via `npx expo start --web` and real magic-link emails read from Mailpit (not mocked). Found and fixed two real RLS bugs that Phase 1's pgTAP suite never caught, because pgTAP exercised `is_band_member()`-gated reads and `service_role` (which bypasses RLS) — this was the first time any `authenticated`-role client request hit these specific policies for real:
  1. **Band creation was completely broken.** `bands_select` only allowed `is_band_member(id)`. Creating a band inserts the `bands` row, then `band_members` — but `supabase-js`'s `.insert().select()` does `INSERT...RETURNING`, and Postgres re-checks the SELECT policy on the new row before returning it. At that instant the creator isn't a `band_members` row yet, so every band creation failed with "new row violates row-level security policy for table bands", 100% of the time, regardless of app code correctness. Fixed in `supabase/migrations/0004_bands_select_own_created.sql`: `bands_select` now also allows `created_by = auth.uid()`.
  2. **Joining a band via invite code was impossible.** Same root cause, different table: a non-member can't `SELECT` a band by `invite_code` to find its id, because `bands_select` (even after fix #1) still only grants access to members or creators — not "anyone who knows the invite code." Fixed in `supabase/migrations/0005_join_band_rpc.sql`: added a `SECURITY DEFINER` `join_band(p_invite_code, p_display_name)` RPC that looks up the band bypassing RLS, then inserts membership. `apps/mobile/app/band-setup.tsx`'s join flow now calls this RPC instead of raw table queries. This also closes most of the gap logged 2026-09-29 (`band_members_insert` had no DB-level invite-code check) — the client no longer has any reason to call the raw insert for joining, though that raw insert path itself is still technically reachable and not yet locked down; full closure of that gap (restricting `band_members_insert` so only `join_band`/band-creation can populate it) is still deferred to Phase 5 as originally planned.
  Both fixes verified live: created a band as one user, joined it as a second user via its real invite code, both landed on the gated home screen with the same `band_id`. Sign-in verified with real Mailpit emails for three different addresses. `emailRedirectTo` added to `signInWithOtp` (using `window.location.origin`) since the default `redirect_to` from local Supabase config pointed at an unreachable port — without it, the session token was never readable by the app (this would have blocked literally every web/native magic-link sign-in, not just testing). Native (iOS/Android) deep-link handling was NOT tested — `detectSessionInUrl: true` only covers the web flow tested here.
